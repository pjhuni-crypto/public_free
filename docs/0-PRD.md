# PRD — 카카오톡 + LLM 시설물 사용신청 챗봇 (시니어 대상)

## 문제 / 배경

동서발전(EWP)이 운영하는 울산 혁신도시 공공기관 편의시설(야외공연장·풋살장·테니스코트 등 6개 시설, 동서발전/동서발전(일산)/근로복지공단/한국산업인력공단 4개 기관 공용)의 사용신청은 현재 회사 CMS 게시판형 웹페이지(www.ewp.co.kr)에서 이루어진다.

- **절차**: 장소 선택 → 시간 선택 → 신청 접수 → 본인인증 → 즉시 자동승인. 기존 웹사이트는 계정 로그인(가입 시 NICE로 1회 실명확인) 기반이라, 신청서 화면 자체에는 별도 인증 입력창이 없다(이름·휴대폰번호가 계정에서 자동으로 채워짐).
- **정책**: 1인 1일 4시간까지, 월 단위 한도, 매월 25일 13시부터 다음 신청 오픈
- **이용대상**: 울산 우정혁신도시 및 울산시 거주 개인/단체

PC/스마트폰 웹 화면에서 장소·시간을 고르고 본인인증까지 순서대로 진행해야 하는 절차는, 온라인 절차에 익숙하지 않은 **지역 시니어 주민**에게 진입장벽이 된다.

## 목표

설치 장벽이 없는 **카카오톡 채널/챗봇**을 통해, **LLM(OpenAI API) 기반 자연어 대화**로 시설 신청 절차를 대행·보조한다. "이번 주 토요일 오후에 풋살장 쓰고 싶어요" 같은 자연스러운 말로 장소·시간을 고르고, 신청서 작성과 본인인증까지 대화로 안내받을 수 있게 한다.

## 타깃 사용자

울산 우정혁신도시 및 울산시 거주 개인·단체 — 특히 기존 웹 신청 절차를 어려워하는 **시니어 주민**을 우선 대상으로 설계한다(버튼/quickReply 중심 UI, 자유 텍스트 입력 최소화, 단계별 확인 반복 등).

## 성공 기준

정량적 목표치(예: 시니어 이용률, 신청 완료율 목표 %)는 아직 정해지지 않았다 — 실 서비스 오픈 후 비즈니스 측에서 정의해야 한다. 정성적으로는 다음을 만족하면 성공으로 본다.
- 시니어 사용자가 별도 앱 설치나 웹사이트 탐색 없이, 카카오톡 대화만으로 신청을 완료할 수 있다.
- 기존 웹 신청과 동일한 정책(4시간/일, 월 한도, 신청 오픈 시각)이 정확히 지켜진다.
- 챗봇이 처리할 수 없는 상황(인증 실패, 시스템 오류 등)에서 사용자가 막히지 않고 상담원 연결 등 다음 행동을 안내받는다.

## 제품 결정 (Product Decisions)

| 결정 | 선택 | 이유 |
|---|---|---|
| 채널 | 카카오톡 채널/챗봇 (카카오 i 오픈빌더 스킬 서버) | 설치 장벽 없음 — 시니어 이탈률을 좌우하는 핵심 요인 |
| LLM | OpenAI API (회사 계정) | 회사 기존 계정 활용 |
| 예약 데이터 소유권 | 새 DB를 만들지 않고 기존 예약 시스템 데이터를 그대로 사용 | 카카오톡은 "새 채널"일 뿐 — 별도 DB를 두면 웹/카톡 채널 간 이중예약 위험 |
| 본인인증 | **카카오 인증서**(카카오써트 전자서명, 앱투앱/채널메시지 인증) — 웹의 NICE 계정 로그인과는 별도로 카카오톡 채널 전용 인증수단으로 신규 도입 | 카카오톡 앱을 벗어나지 않고 인증 완료 가능(NICE 웹뷰 이동보다 단계가 훨씬 적음) — 시니어 마찰 최소화가 이 프로젝트의 핵심 목표와 직결 |
| 인증 연동 소유 | **스킬 서버**가 카카오인증서 API를 직접 호출, 예약서버는 그 결과(서버간 API 키로 인증된 요청)만 신뢰 | 카카오인증서는 카카오 채널에 종속적인 인증수단이라 채널을 담당하는 스킬서버가 갖는 게 자연스러움. 예약서버(백엔드팀)는 NICE 외에 새 벤더 연동을 배울 필요가 없어짐 |
| 배포 | Vercel + Vercel KV | 사내 서버 프로비저닝·DMZ 협의 없이 HTTPS 엔드포인트를 빠르게 확보 |

## 이번 프로젝트 범위 (In Scope)

- 카카오 스킬 서버(챗봇) + LLM 오케스트레이션 레이어 구현
- 예약 API 계약(OpenAPI) 설계 + 그 계약을 만족하는 Mock 서버 구현(백엔드가 아직 없는 동안 개발/테스트용)
- 장소 선택 → 시간 선택 → 신청서 작성 → 카카오인증서 본인인증(앱 내 승인 + 복귀 확인) → 제출/승인 결과 안내까지의 대화 흐름
- 프로토타입 단계에서는 실제 카카오인증서 계약 없이 **Mock으로 인증 흐름을 시뮬레이션**(자동/수동 승인, 가짜 신원정보 반환)하여 대화 로직만 먼저 검증

## 이번 프로젝트 범위 밖 (Out of Scope) / 확장 후보

- **실제 예약 백엔드 API 구현** — 회사 내 다른 팀이 기존 예약 시스템에 API를 노출하는 방식으로 별도 진행. 상세는 `1-domain-definition.md`의 계약 정의 및 아래 "의존성" 참조.
- 내 신청 조회/취소
- 카카오 알림톡/친구톡을 통한 인증완료 자동 푸시
- 매월 25일 13시 신청 오픈 리마인더 알림
- 실시간 상담원 핸드오프 연동
- 다국어 지원, 관리자 대시보드

## 의존성 및 전제조건

- **백엔드팀**: 기존 예약 시스템에 예약 API 계약(`1-domain-definition.md` 참조)을 노출해야 실서비스가 가능하다. Mock 서버로는 챗봇 개발/테스트만 가능하고 실제 신청은 되지 않는다.
- **카카오 비즈니스 채널 + 오픈빌더 계정** — 아직 없다면 이번 구현 범위 밖에서 별도 준비 필요.
- **Vercel 계정** — 이번 구현 범위 밖에서 별도 준비 필요.
- **카카오 인증서(카카오써트) 계약**: 카카오가 아니라 바로써트·링크허브 같은 인증 중계 VAN사를 통해 계약하는 구조이며, 계약 주체는 반드시 **동서발전(법인/기관)**이어야 한다 — 개인 명의 앱으로는 실사용자 대상 서비스에 쓸 수 없다(전자서명법·개인정보보호법상 이용기관 요건). 비용은 종량제/정액제 협의사항이라 공개된 고정가가 없어 카카오써트(1666-0044) 또는 중계 VAN사에 별도 견적 확인이 필요하다. 이 계약이 되기 전까지는 Mock으로만 개발·검증 가능.
- 카카오톡 채널/오픈빌더(챗봇 껍데기) 자체는 개인 계정으로 프로토타입 제작이 가능하지만, 실사용자 정보를 다루고 실제 예약서버와 연결되는 시점부터는 회사 명의 전환이 필요.

## 열린 리스크

- 기존 예약 시스템이 API로 노출하기 쉬운 구조인지(레거시 서버사이드 렌더링이면 API 계층 추가 공수가 커짐) — 코드베이스 확인 필요.
- 매월 25일 13시 신청 오픈 시 카카오톡 채널을 통한 신청 몰림 처리(동시성 제어)는 기존 시스템 책임으로 가정하되 확인 필요.
- 성공 기준의 정량적 목표치가 아직 없음 — 비즈니스 측 정의 필요.
- **시니어 대상 생체인증/PIN 접근성**: 카카오인증서가 NICE 웹뷰보다 단계는 훨씬 적지만, "알림 인지 → 지문/PIN 승인"이라는 본인확인 액션 자체는 여전히 남는다. 이게 실제로 시니어에게 얼마나 쉬운지는 Mock 테스트로는 확인할 수 없고, 계약 후 **실기기·실사용자 테스트**가 반드시 필요하다.
